# 面向用户的预测功能:三要素(区间/依据/置信度)+回测校准闭环

场景
任何面向C端用户的预测类功能(习惯预测/健康预测/消费预测/风险预警)。用户看到"预计6根"会立刻问"凭什么/准不准", 答不上来预测就摧毁信任而非建立信任。

做法
1. 三要素缺一不可:
   - 区间: projected ± spread, spread按置信度分档(高0.2/中0.3/低0.45)。单点数字显得精确但不可信
   - 依据: 一句话说明来源("按你最近两周的同时段节奏"/"按你今天的记录速度")。用户知道"为什么"才会信
   - 置信度: 按样本量分档(高/中/低), 样本不足时明说"记录还少, 先以实际进度为准"
2. 预测落库做回测: 每天把预测值快照落库(同一天去重, 只留最新), 次日读快照 vs 当日实际 → bias=(actual-projected)*阻尼系数 → 加到今日预测上
3. 夹逼防跑偏: bias修正后夹在 [0.6x, 1.4x] 原值区间, 避免单日异常把预测带飞
4. 透明标注: 校准生效时前端显示"已按昨天实际微调", 让用户感知系统在学

原因
- 预测价值 = 准确性 × 可信度。单点精确数字看似专业, 实则在样本不足时必然失准, 反而伤害信任
- 回测校准是数据飞轮: 用户越用→数据越多→预测越准→越愿意用。竞品的"预测"多停留在静态模式识别("你周三容易破戒"), 动态实时预测+回测校准是差异化
- 零LLM: 数值预测必须用确定性规则, LLM数值判断不可靠且昂贵(呼应项目铁律"数值计算不用LLM")

反例
- 只给单点数字不给区间/依据 → 用户觉得"AI瞎说"
- 样本<14天就强行给"高置信度"预测 → 必然打脸
- 校准不夹逼 → 某天异常值(如生病没记录)把预测带偏一整周
- 每次预测都重算快照 → 失去"预测当时值"的对照基准, 无法回测

验证
challengePlanet 实测: 单测40例+集成12例(校准闭环: 昨日预测5实际3→bias=-1→今日预测下调)+e2e 13例全绿
